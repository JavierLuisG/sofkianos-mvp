## 1. Análisis de Técnicas de Diseño de Pruebas (ISTQB)

Para esta historia de usuario, se han aplicado las siguientes técnicas de caja negra:

-   **Partición de Equivalencia:** Para validar las categorías de Kudos (Innovation, Teamwork, Passion, Mastery, Todas) y los rangos de fechas.

-   **Análisis de Valores Límite:** Aplicado específicamente a la lógica de fechas (`startDate` vs `endDate`) y al tiempo de _debounce_ de 500ms.

-   **Pruebas de Transición de Estados:** Para validar el comportamiento de los componentes (habilitado/deshabilitado) durante la carga de datos (estado `loading`).

-   **Pruebas Basadas en Casos de Uso:** Para asegurar que el flujo de "Limpiar filtros" retorne al usuario al estado inicial del sistema.


----------

## 2. Casos de Prueba en Lenguaje Gherkin

### Grupo A: Búsqueda de Texto y Debounce

**Caso de Prueba 01: Validación de tiempo de espera (Debounce) en búsqueda**

-   **given**  que el usuario se encuentra en la pantalla de historial de Kudos

-   **when**  el usuario ingresa el texto "Innovación" en el campo "Buscar en de, para, mensaje..."

-   **and**  transcurren menos de 500ms sin que el usuario deje de escribir

-   **then**  el sistema no debe disparar la petición de filtrado  `onFilter`

-   **and**  al pausar la escritura por más de 500ms, el sistema debe ejecutar la búsqueda automáticamente.


**Caso de Prueba 02: Búsqueda por contenido parcial en mensajes**

-   **given**  que existen Kudos con mensajes que contienen la palabra "Excelencia"

-   **when**  el usuario ingresa "Excel" en el campo de búsqueda de texto

-   **then**  el sistema debe mostrar únicamente los Kudos que contienen dicho fragmento en el mensaje, remitente o destinatario.


----------

### Grupo B: Categorías y Fechas

**Caso de Prueba 03: Filtrado por categoría específica**

-   **given**  que el usuario despliega el selector de categorías

-   **when**  el usuario selecciona la opción "Teamwork"

-   **and**  presiona el botón "Aplicar Filtros"

-   **then** la lista debe actualizarse para mostrar solo los Kudos asociados a la categoría "Teamwork".


**Caso de Prueba 04: Selección de todas las categorías**

-   **given**  que la lista está filtrada por "Passion"

-   **when**  el usuario cambia la categoría a "Todas"

-   **and**  presiona "Aplicar Filtros"

-   **then** el sistema debe mostrar los Kudos de las cuatro categorías predefinidas (Innovation, Teamwork, Passion y Mastery).


**Caso de Prueba 05: Validación de rango de fechas erróneo (Límite)**

-   **given**  que el usuario selecciona en "Fecha desde" el día 20-10-2025

-   **when**  el usuario selecciona en "Fecha hasta" el día 15-10-2025

-   **then**  el sistema debe mostrar un mensaje de error indicando que la fecha de inicio no puede ser posterior a la fecha fin.


----------

### Grupo C: Acciones y Estados de Interfaz

**Caso de Prueba 06: Limpieza de criterios de búsqueda**

-   **given**  que el usuario tiene activos filtros de texto, categoría y fechas

-   **when**  el usuario presiona el botón "Limpiar"

-   **then**  todos los campos del formulario deben volver a sus valores por defecto

-   **and**  la lista de Kudos debe recargarse sin filtros aplicados.


**Caso de Prueba 07: Control de interactividad durante la carga (Loading)**

-   **given**  que el sistema está recuperando datos de la API (estado de carga activo)

-   **when**  el usuario intenta interactuar con los inputs o botones de filtro

-   **then**  todos los elementos del componente  `KudoFilters`  deben permanecer en estado  `disabled`

-   **and**  se debe visualizar un spinner de carga indicando la actividad del sistema.


----------

### Grupo D: Reglas de Negocio y Responsive

**Caso de Prueba 08: Búsqueda sobre correos enmascarados (Privacidad)**

-   **given** que el sistema enmascara los correos electrónicos (ej: j*z@domain.com)

-   **when**  el usuario intenta buscar un Kudo ingresando un correo completo que no coincide con el formato enmascarado visible

-   **then**  el sistema debe ser capaz de procesar la búsqueda internamente y retornar los resultados correspondientes si el texto coincide con la lógica de búsqueda del backend.


**Caso de Prueba 09: Adaptabilidad visual en dispositivos móviles**

-   **given**  que el usuario accede al sistema desde un navegador con resolución de pantalla inferior a 768px (Mobile)

-   **when**  se visualiza el componente de filtros

-   **then**  los campos de búsqueda, categorías y fechas deben mostrarse en una disposición vertical (Stack vertical).


**Caso de Prueba 10: Adaptabilidad visual en escritorio**

-   **given**  que el usuario accede desde un navegador en resolución superior a 1024px (Desktop)

-   **when**  se visualiza el componente de filtros

-   **then**  los campos de búsqueda deben mostrarse en una disposición horizontal para optimizar el espacio en pantalla.

### Análisis de Calidad y Refinamiento (ISTQB)

Para garantizar una cobertura exhaustiva, he aplicado las siguientes técnicas de diseño:

-   **Partición de Equivalencia (EP):** Clasificación de categorías (Innovation, Teamwork, Passion, Mastery, Todas) y estados de carga (Loading/Idle).

     

-   **Análisis de Valores Límite (BVA):** Aplicado al _debounce_ de **500ms** y a la comparación de fechas (`startDate` vs `endDate`).

-   **Pruebas de Transición de Estados:** Verificación de la interactividad de los campos (Disabled/Enabled) mientras el sistema procesa peticiones asíncronas.

     

-   **Pruebas de Casos de Uso:** Escenarios de búsqueda de Kudos basados en los flujos de consulta y enmascaramiento de identidad.

### Casos de Prueba Refinados (Lenguaje Gherkin)

#### 1. Flujos Básicos y Reglas de Negocio

**Caso de Prueba 01: Filtrado exitoso por categoría única**

-   **Dado** que el usuario visualiza la lista de Kudos en el panel de historial.

     

-   **Cuando** el usuario selecciona la categoría **"Innovation"** en el desplegable de filtros.

     

-   **Y** presiona el botón **"Aplicar Filtros"**.

-   **Entonces** el sistema debe enviar la solicitud de filtrado a través de la propiedad `onFilter`.

-   **Y** la lista debe mostrar únicamente los reconocimientos etiquetados bajo la categoría **"Innovation"**.

     


**Caso de Prueba 02: Búsqueda interactiva con retraso (Debounce)**

-   **Dado** que el cursor está posicionado en el campo con el placeholder **"Buscar en de, para, mensaje..."**.

-   **Cuando** el usuario escribe la palabra "Mastery" de forma continua.

-   **Entonces** el componente no debe ejecutar ninguna búsqueda mientras el usuario escribe.

-   **Y** el sistema debe disparar la actualización de resultados solo después de que transcurran **500ms** de inactividad en el teclado.


**Caso de Prueba 03: Reinicio de criterios (Botón Limpiar)**

-   **Dado** que el usuario tiene activos filtros de texto, una categoría específica y un rango de fechas.

-   **Cuando** el usuario presiona el botón **"Limpiar"**.

-   **Entonces** el formulario debe restablecer el campo de búsqueda a vacío, la categoría a **"Todas"** y las fechas a sus valores nulos.

-   **Y** la lista de Kudos debe recargarse automáticamente mostrando todos los registros disponibles sin filtros.

     


----------

#### 2. Validaciones y Excepciones (Análisis de Límites)

**Caso de Prueba 04: Validación de coherencia cronológica (Error de Fechas)**

-   **Dado** que el usuario selecciona una **"Fecha desde"** posterior a la **"Fecha hasta"** (ej: Inicio 04/03/2026 y Fin 01/03/2026).

-   **Cuando** el usuario intenta aplicar los filtros.

-   **Entonces** el sistema debe impedir el envío de la petición.

-   **Y** debe mostrar un mensaje de error indicando que el rango de fechas es inválido.


**Caso de Prueba 05: Comportamiento ante búsqueda sin criterios**

-   **Dado** que todos los campos de filtro están vacíos o en sus valores por defecto.

-   **Cuando** el usuario presiona el botón **"Aplicar Filtros"**.

-   **Entonces** el sistema debe mostrar un aviso al usuario indicando que no se han seleccionado criterios de búsqueda.


----------

#### 3. Estados de Interfaz y Experiencia de Usuario (UX)

**Caso de Prueba 06: Bloqueo de controles durante la carga de datos**

-   **Dado** que el sistema ha iniciado una petición de consulta y está en estado de carga.

-   **Cuando** el usuario intenta modificar el campo de texto o las categorías.

-   **Entonces** todos los campos del formulario deben estar en estado **deshabilitado**.

-   **Y** se debe visualizar un **spinner de carga** como feedback visual de la búsqueda activa.


**Caso de Prueba 07: Búsqueda sobre datos enmascarados (Privacidad)**

-   **Dado** que los correos electrónicos de los empleados se muestran con formato enmascarado (ej: j*z@sofka.com).

     

-   **Cuando** el usuario ingresa un fragmento del correo en el campo de búsqueda de texto.

-   **Entonces** el sistema debe filtrar y retornar los Kudos cuyos correos (aunque estén enmascarados en la vista) coincidan internamente con la búsqueda.
